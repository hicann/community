# CANN 社区废弃特性规范

---

## 1 目的

本规范指导CANN社区对外开放特性的统一废弃（Deprecation）与删除（Removal），确保：

- 用户在特性被删除前获得**充分的预告时间**与**明确的迁移指引**；
- 废弃过程**可追溯、可评审、可管控**；
- 内部代码与对外资料**同步演进**，避免资料与代码不一致；
- 试验特性与正式特性采用**差异化的生命周期管理**。



---

## 2 术语与定义

| 术语 | 定义 |
|---|---|
| **废弃（Deprecation）** | 接口或头文件被标记为不再推荐使用，但仍保留声明与实现，编译/运行时产生告警 |
| **删除（Removal）** | 接口或头文件的声明、实现及相关文档从 CANN 中彻底移除 |
| **Major 版本** | 版本号格式 `X.Y.Z` 中的 `X`，如 `9.2.1` 中的 `9` |
| **Minor 版本** | 版本号格式 `X.Y.Z` 中的 `Y`，如 `9.2.1` 中的 `2` |
| **Patch 版本** | 版本号格式 `X.Y.Z` 中的 `Z`，如 `9.2.1` 中的 `1` |
| **普通接口** | 正式特性所有对外开放 API接口 |
| **试验特性（Experimental）** | 标记为试验性的 API接口 |
| **废弃声明版本** | 首次在公开资料中声明废弃的版本 |
| **删除版本** | 实际执行删除的版本 |

---

## 3 适用范围

本规范适用于 CANN 对外开放的全部内容，包括但不限于：

- **API 接口**：C/C++ 函数、Python 函数、类及其成员、宏定义、环境变量
- **头文件**：`.h` / `.hpp` 对外发布的头文件
- **试验特性**：已标记为 experimental 的 API接口



---

## 4 废弃流程总览

```
                     ┌─────────────┐      ┌────────────┐     ┌────────────────┐
  前提： 评审通过 ──> │ 1. 废弃声明  │ ──>  │ 2. 废弃合入 │ ──> │ 3. 删除合入    │
                     │   (提前发布) │      │    (告警)  │     │ (接口/代码删除) │
                     └─────────────┘      └────────────┘     └────────────────┘
```

## 5 规范条款

### 5.1 废弃声明要求（规范1）

**允许在Major版本或Minor版本声明废弃特性，其中正式特性接口需要至少提前 1 年（>=1年）在版本公开资料中声明废弃接口/头文件的名称与删除日期，试验特性接口需要至少提前1个Minor版本在公开资料中声明废弃接口/头文件的名称与删除日期。**

#### 5.1.1 公开资料范围

公开资料包含但不限于：

| 资料类型 | 废弃信息呈现位置 |
|---|---|
| 版本说明书（Release Notes） | "删除与废弃特性" 章节 |
| 接口 API 文档 | 组件“废弃接口列表”章节 |
| 头文件注释 | 接口声明的 `@deprecated` 标签 |

#### 5.1.2 声明内容要求

每个废弃接口/头文件的声明必须包含：

- 接口/头文件名称
- **删除日期**
- **推荐或替换接口**（可选）

#### 5.1.3 声明废弃参考模板

```
模板格式：XXX_old接口在CANN X.Y.0版本标记为废弃，将在xxxx年x月xx日之后的版本删除，替换为：XXX_new接口。
例如：aclnnGroupedMatmul接口在CANN 9.0.0版本标记为废弃，将在2027年3月30日之后的版本删除，替换为：aclnnGroupedMatmulV5。
```

---

### 5.2 删除版本（规范2）

#### **5.2.1 正式特性接口（规范2.1）**

**正式特性的接口在 `X.Y.0` 版本（含 Major & Minor）声明废弃后，默认在 `(X+N).0.0` 的Major 版本集中删除接口与代码。**

参考：

| 声明废弃版本 | 删除版本 | 示例 |
|---|---|---|
| 9.0.0 ~ 9.3.0 | **11.0.0** | 在 9.0.0~9.3.0 任一版本声明废弃 → 11.0.0 集中删除 |

#### **5.2.2 试验特性接口（规范2.2）**

**试验特性的接口在 `X.Y.0` 版本（含 Major & Minor）声明废弃后，允许在 `(X+N).0.0` 的Major 版本或者`X.(Y+N).0` 的Minor 版本集中删除接口与代码。**

参考：

| 声明废弃版本 | 删除版本  | 示例                              |
| ------------ | --------- | --------------------------------- |
| 9.1.0        | **9.2.0** | 在 9.1.0版本声明废弃 → 9.2.0 删除 |

#### 5.2.3 例外评审（规范2.3）

**特殊接口希望提前删除或保留更长时间，需要专门评审。**

| 声明废弃版本 | 删除版本   | 示例                               |
| ------------ | ---------- | ---------------------------------- |
| 9.1.0        | **10.0.0** | 在 9.1.0版本声明废弃 → 10.0.0 删除 |

### 5.3 资料更新（规范3）

**在资料中删除废弃接口/头文件原来的描述说明，并在废弃列表中增加该废弃接口。**

#### 5.3.1 操作要求

- **API 文档**：从正式接口描述章节中移除该接口的详细说明
- **版本说明书**：在"删除与废弃特性"章节新增条目
- **接口声明头文件**：保留废弃接口的声明位置但标注废弃提示（见 5.4）
- **废弃接口列表**：在"废弃接口列表"章节中添加废弃接口信息，包含本规范 5.1.3 的声明模板全部字段

#### 5.3.2 废弃接口列表参考模板

| 接口名称 | 类型 | 废弃版本 | 删除版本 | 替换接口 | 状态 |
|---|---|---|---|---|---|
| `aclnnGroupedMatmul()` | 普通接口 | 9.0.0 | 11.0.0 | `aclnnGroupedMatmulV5()` | 已废弃，待删除 |

---

### 5.4 头文件废弃标记（规范4）

**当前版本保留旧接口的声明及实现，但在接口声明头文件（例如 `.h`）的注释说明接口废弃提示（deprecated），包含接口删除日期、推荐或替换的接口等信息。**

#### 5.4.1 标记格式

头文件中废弃接口的声明参考格式：

```cpp
#define <组件名>_DEPRECATED [[deprecated("Deprecated since <废弃版本>，Will be removed after <删除日期>，Use <替换接口> instead.")]]

/*
 * @deprecated Deprecated since <废弃版本>， Will be removed in <删除日期>，Use <替换接口> instead.
 *
 * <接口功能描述>
 */
<组件名>_DEPRECATED <返回类型> <接口名>(<参数列表>);
```

#### 5.4.2 标记实例

```cpp
#define RTS_DEPRECATED [[deprecated("Deprecated since 9.0.0，Will be removed after 2027/3/30， Use aclFooBarV2 instead.")]]

/*
 * @deprecated Deprecated since 9.0.0，Will be removed after 2027/3/30，Use aclFooBarV2 instead.
 *
 * Get the foo bar value.
 *
 * @param[out] value The foo bar value.
 * @return ACL_SUCCESS on success, other error codes on failure.
 */
RTS_DEPRECATED aclError aclFooBar(int* value);
```

#### 5.4.3 Doxygen 标签要求

头文件注释中必须包含以下 Doxygen 标签：

| 标签 | 内容 |
|---|---|
| `@deprecated` | 废弃声明，包含废弃版本、删除版本、替换接口 |
| `@param` | 参数说明（保留原有） |
| `@return` | 返回值说明（保留原有） |

---

### 5.5 编译告警与运行日志告警（规范5）

**【只适用于接口】在代码中增加废弃接口编译告警提示和首次运行日志告警提示，告警内容包含废弃信息提示、接口删除日期、推荐或替换的接口等。**

#### 5.5.1 编译告警

通过 5.4 条定义的 `<组件名>_DEPRECATED` 宏实现编译时告警。用户调用废弃接口时，编译器产生 deprecation 告警。

告警内容必须包含：

- 废弃信息提示
- 接口删除日期（版本号）
- 推荐或替换的接口

告警示例（GCC）：

```
warning: 'aclError aclFooBar(int*)' is deprecated: Deprecated since 9.0.0，Will be removed after 2027/3/30， Use aclFooBarV2 instead. [-Wdeprecated-declarations]
```

【说明】只适用于C/C++，python不涉及。

#### 5.5.2 首次运行日志告警

废弃接口在被调用时，需在**首次调用**时输出运行时日志告警。实现要求：

- **仅首次调用告警**：使用 `static once_flag` 或等价机制确保同一接口在同一进程内只告警一次
- **日志级别**：WARNING
- **日志内容**：与编译告警一致，包含废弃信息、删除日期、替换接口

运行时告警示例代码：

```cpp
#include <mutex>

aclError aclFooBar(int* value) {
    static std::once_flag flag;
    std::call_once(flag, [] {
        ASCEND_LOGW("aclFooBar is deprecated since 9.0.0，will be removed after 2027/3/30，use aclFooBarV2 instead");
    });
    // ... 原有实现 ...
    return ACL_SUCCESS;
}
```

运行时告警示例日志：

```
[WARNING] aclFooBar is deprecated since 9.0.0，Will be removed after 2027/3/30，use aclFooBarV2 instead
```

#### 5.5.3 告警内容规范

编译告警与运行日志告警的文案需保持一致，格式统一为：

```
<接口名> is deprecated since <废弃版本>， will be removed after <删除日期>，use <替换接口> instead.
```

如无替换接口，则为：

```
<接口名> is deprecated since <废弃版本>，will be removed in <删除日期>.
```

### 5.6 新旧接口同步落地（规范6）

**若废弃接口存在替换的新接口时，则新接口上线和旧接口声明废弃在同一个版本落地。**

#### 5.6.1 操作要求

若废弃接口存在替换新接口的话，则当废弃旧接口时，则其替换接口（新接口）必须在**同一版本**中：

- 完成开发并通过测试
- 在 API 文档中正式发布
- 头文件中提供完整声明与 Doxygen 文档

#### 5.6.2 版本落地清单

同一版本合入时需同时包含：

| 项目 | 要求 |
|---|---|
| 旧接口头文件废弃标记 | 加 `DEPRECATED` 宏 + `@deprecated` Doxygen 注释 |
| 旧接口编译告警 | 确认三大编译器均产生告警 |
| 旧接口运行时告警 | 实现 `call_once` 首次调用日志 |
| 新接口声明与实现 | 头文件声明 + 完整实现 + 单元测试 |
| 新接口文档 | API 文档发布 |
| 废弃接口列表更新 | 废弃接口列表新增废弃条目 |

---

### 5.7 删除执行（规范7）

**到了宣称的删除版本发布时，将旧接口和代码同时删除。**

#### 5.7.1 删除内容

在删除版本发布时，需彻底移除：

| 删除项 | 说明 |
|---|---|
| 接口声明 | 从头文件中移除函数声明 |
| 接口实现 | 从源文件中移除函数定义 |
| 编译告警宏 | 移除仅用于该接口的 `DEPRECATED` 宏（如其他接口仍在使用则保留） |
| 运行时告警代码 | 移除 `call_once` 日志代码 |
| API 文档 | 从废弃接口列表中移除该条目，标记为"已删除" |
| 测试用例 | 移除针对该废弃接口的测试 |

#### 5.7.2 删除验证

- 删除后编译通过，无残留引用
- 在版本的 Release Notes 中记录"删除与废弃特性"章节下，将废弃接口修改成删除接口。

#### 5.7.3 版本 Release Notes 删除特性模板参考

```
模板格式：XXX_old接口在CANN X.Y.0版本标记为废弃，在本版本删除，替换为：XXX_new接口。
```

## 6 流程合规检查清单

每次版本发布前，需按以下清单逐项检查：

| 序号 | 检查项 | 对应规范 | 通过标准 |
|---|---|---|---|
| 1 | 公开资料是否提前声明废弃 | 5.1 | Release Notes + API 文档均含废弃声明 |
| 2 | 删除版本是否符合要求 | 5.2 | 普通接口 X+N major主版本删除（N由评审决定）/ 试验接口主版本（major）和次版本（minor）都可以删除/特殊接口单点评审 |
| 3 | 资料是否更新（移至废弃列表） | 5.3 | 正式章节已移除，废弃列表已新增 |
| 4 | 头文件是否添加 DEPRECATED 标记 | 5.4 | 宏 + Doxygen `@deprecated` + 删除日期 + 替换接口（可选） |
| 5 | 编译告警是否正常触发（只适用于C/C++） | 5.5.1 | GCC/Clang/MSVC 三大编译器均产生告警 |
| 6 | 首次运行日志告警是否实现 | 5.5.2 | `call_once` 机制 + WARNING 级别 |
| 7 | 新旧接口是否同步落地（可选） | 5.6 | 若存在新接口替换，则同一版本含新接口声明+实现+文档 |
| 8 | 删除版本是否按期删除 | 5.7 | 接口声明+实现+文档+测试全部移除 |

## 7. 附则

本指南由 CANN 社区负责维护与更新，修订需经评审通过后生效。
